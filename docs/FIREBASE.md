# Firestore як база даних

Використовується, коли `DB_BACKEND=firestore` — типово для Vercel.
На власному сервері краще лишити `sql`: Postgres поруч у Docker швидший і
не тарифікується за кожну операцію читання.

---

## Чому Firestore підходить для serverless

| | Postgres на Vercel | Firestore |
|---|---|---|
| З'єднання | Ліміт конектів, потрібен pooler | HTTP, ліміту немає |
| Холодний старт | Конект ~100–300 мс | Немає конекту взагалі |
| Ціна на малих обсягах | Neon free → потім $19+ | 50k читань/день безкоштовно |
| Складна аналітика | SQL будь-якої глибини | Тільки те, що денормалізовано |

---

## Що змінюється в моделі даних

Firestore не має JOIN, GROUP BY і типу Decimal. Три наслідки:

**Гроші зберігаються в копійках (int).** Поля мають суфікс `_cents`:
`price_cents`, `total_spent_cents`. Float для грошей дає помилки округлення,
тому конвертація відбувається на межі репозиторію, а бізнес-логіка як і раніше
працює з `Decimal`.

**Лічильники підтримуються при записі.** `orders_count`, `total_spent_cents`,
`referrals_count` у клієнта; `products_count` у категорії; `used_count` у
промокоді. Оновлюються атомарними інкрементами. У SQL те саме — щоб поведінка
двох баз не розходилась.

**Пошук — префіксний.** Firestore не вміє шукати підрядок. Товари шукаються
діапазоном по `name_lower`; клієнти й замовлення — фільтрацією по
денормалізованому `search_key` на боці застосунку (це адмінські списки,
не гарячий шлях).

## Налаштування

### 1. Проєкт

[console.firebase.google.com](https://console.firebase.google.com) → Create project
→ Firestore Database → Create database → **Production mode**, регіон
`europe-central2` (Варшава — найближчий до України).

### 2. Сервісний акаунт

Project settings → Service accounts → Generate new private key. Завантажиться
JSON — це ключ від бази, поводьтесь із ним як із паролем.

### 3. Індекси та правила

```bash
npm install -g firebase-tools
firebase login
firebase use --add           # оберіть свій проєкт

firebase deploy --only firestore:indexes
firebase deploy --only firestore:rules
```

`firestore.indexes.json` містить 22 складені індекси, виведені з коду
`shop/repo/firestore.py` — по одному на кожну комбінацію «фільтри плюс
сортування», яку роблять бот, вітрина й панель. Універсального індексу в
Firestore немає.

Без них запит падає з `FAILED_PRECONDITION`. У панелі це видно як 500, а в
боті — як **порожній каталог**: помилка ловиться й показується порожнім
списком, тож причина неочевидна. Індекси спершу мають статус *Building*;
поки не стануть *Enabled*, помилка триває.

> Додаєте новий запит у `firestore.py` — одразу дописуйте індекс сюди.
> Створений вручну за посиланням з логів у файл не потрапляє.

`firestore.rules` забороняє будь-який прямий доступ. Це правильно: до бази
ходить лише бекенд через сервісний акаунт, а Admin SDK правила обходить.
Ні бот, ні панель до Firestore напряму не звертаються.

### 4. Змінні оточення

Локально:

```bash
export DB_BACKEND=firestore
export FIREBASE_PROJECT=ваш-проєкт-id
export GOOGLE_APPLICATION_CREDENTIALS=/шлях/до/ключа.json
```

На Vercel файл покласти нікуди, тому вміст ключа передається однією змінною:

```
DB_BACKEND=firestore
FIREBASE_PROJECT=ваш-проєкт-id
GOOGLE_APPLICATION_CREDENTIALS_JSON=<увесь вміст JSON одним рядком>
```

`api/index.py` розгортає її у тимчасовий файл при старті функції.

### 5. Наповнення каталогу

```bash
DB_BACKEND=firestore PYTHONPATH=backend python backend/seed.py
```

## Тестування

Логіка репозиторію Firestore покрита тестами через `InMemoryDocStore` —
сховище на пам'яті, яке повторює обмеження Firestore (жодних JOIN, тільки
підтримувані оператори):

```bash
cd backend
python tests_repo.py      # 62 перевірки × 2 бази + звірка на розбіжності
python tests_api.py       # 60 перевірок HTTP × 2 бази
```

**Що ці тести не покривають:** тонкий адаптер `shop/repo/firestore_store.py` —
прямі виклики SDK. Перед продакшеном прогоніть контрактні тести проти
справжнього емулятора:

```bash
firebase emulators:start --only firestore
FIRESTORE_EMULATOR_HOST=localhost:8080 \
  FIREBASE_PROJECT=demo-shop \
  PYTHONPATH=$PWD python tests_repo.py --real
```

Якщо результат збігається з in-memory прогоном — адаптер коректний.

## Обмеження, про які варто знати

**Лічильники id.** Firestore не має автоінкременту, тому послідовності
тримаються в колекції `_counters` і рухаються транзакційно. Один документ
витримує близько одного запису на секунду. Для магазину це з великим запасом,
але при десятках замовлень за секунду знадобиться розподілений лічильник
із шардами.

**Статистика читає всі оплачені замовлення.** Firestore не вміє агрегувати
по днях, тому графік і топ товарів рахуються в застосунку. До кількох тисяч
замовлень це непомітно; далі варто складати денні підсумки в окрему колекцію
при зміні статусу замовлення.

**Ціна за операції.** Кожен показ каталогу — це читання документів. Безкоштовна
квота 50 000 читань на добу покриває приблизно 1500–2500 сеансів у боті.
Перевищення тарифікується копійками, але за динамікою варто стежити в консолі.

**Немає транзакцій між колекціями в поточній реалізації.** Створення
замовлення й списання залишків — окремі операції. У SQL те саме, тому
поведінка однакова; при збої між ними можливе розходження. Якщо це критично,
загорніть `create_order` у транзакцію Firestore.
