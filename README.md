# Телеграм-магазин: Mini App + бот + панель

Магазин у Telegram із веб-панеллю керування. Бот на aiogram 3, API на FastAPI,
панель на React. Спільне ядро (`backend/shop/`) — щоб бот і дашборд працювали
з однією логікою і не розходились у поведінці.

---

## Що вміє

**Вітрина Mini App** — основний вхід для покупця
- Каталог із пошуком і рейкою категорій, кошик, оформлення в одному вікні
- Підтвердження віку 18+ перед доступом до каталогу
- Профіль: бонуси, реферальне посилання, історія замовлень
- Тема підхоплюється з клієнта Telegram — виглядає рідною в темній і світлій
- Автентифікація через підписаний `initData`: підробити чужий `tg_id` неможливо

**Бот** — запасний шлях і сповіщення
- Підтвердження віку 18+ на першому кроці — без нього каталог недоступний
- Каталог: категорії → товари з пагінацією, фото, залишками
- Кошик із зміною кількості прямо в картці товару
- Оформлення: ім'я → телефон → місто → адреса → промокод → бонуси → оплата → підтвердження
- Оплата переказом на картку з надсиланням квитанції, або накладений платіж
- Профіль: історія замовлень, бонусний баланс, реферальне посилання
- Реферальна програма: % бонусами від кожного виконаного замовлення запрошеного
- Кнопки зміни статусу просто в адмін-чаті, куди падають нові замовлення
- Працює **лише в особистому чаті**: у групах і каналах віддає привітання
  з кнопкою переходу, щоб чужі бонуси й адреси не потрапили в спільний чат

**Дашборд**
- Огляд: виручка, середній чек, нові замовлення, графік по днях, топ товарів
- Замовлення: фільтри, пошук, зміна статусу, нотатки менеджера
- Каталог: CRUD товарів і категорій, швидка зміна залишків, індикатор «закінчується»
- Клієнти: історія покупок, ручне нарахування бонусів, блокування
- Промокоди: відсоткові та фіксовані, ліміти загальні й на клієнта, термін дії
- Розсилки: 6 сегментів, попередній підрахунок охоплення, прогрес наживо
- Налаштування: реферальний %, ліміт бонусів, вік, реквізити, назва й валюта —
  редагуються без редеплою
- Два види видалення скрізь: приховати (зникає з бота, лишається в історії)
  або стерти назавжди

## Розгортання

**Покроковий посібник — [docs/SERVER.md](docs/SERVER.md).**
Там усе від підготовки Ubuntu до перевірки, що замовлення доходить у групу.

Цільове розгортання — **власний сервер**: Docker Compose піднімає Postgres,
Redis, API, бота, планувальник, панель, вітрину й nginx з TLS. Назовні
відкриті лише 80 і 443.

| Компонент | Що робить |
|---|---|
| База | Postgres, міграції накочує окремий сервіс |
| Бот | polling; вебхук лишається як опція |
| Розсилки | негайні — фоном, відкладені — планувальником, з тихими годинами |
| Бекапи | `pg_dump` за розкладом з панелі, з автоочисткою старих дампів |

Панель і API завжди на одному домені — інакше панель не знайде бекенд.

База — власна: Postgres у контейнері поруч, назовні не відкритий. Зовнішніх
сервісів для зберігання даних немає взагалі.

Автозапуск після перезавантаження забезпечує systemd-юніт `elfar.service`.
Самої лише політики `restart: always` у compose для цього не досить: вона
піднімає контейнер, який упав, але не той, який зупинили через
`docker compose down` — а саме так виглядає коректне вимкнення сервера.

Бізнес-логіка від бази не залежить: бот і API працюють через інтерфейс
`Repository` з двома реалізаціями, а тести перевіряють, що вони поводяться
однаково.

### Локальний запуск (розробка)

```bash
cp .env.example .env
nano .env                    # заповніть BOT_TOKEN, ADMIN_IDS, паролі

docker compose up -d --build
docker compose exec bot python seed.py     # демо-каталог (за бажанням)
```

Дашборд: `http://localhost` — логін і пароль з `.env`.
API-документація: `http://localhost:8000/docs`.

### Без Docker

```bash
cd backend
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
export PYTHONPATH=$PWD

alembic upgrade head                             # схема бази (для DB_BACKEND=sql)
python -m bot                                    # термінал 1
uvicorn api.main:app --reload --port 8000        # термінал 2

cd ../dashboard && npm install && npm run dev    # термінал 3
```

## Обов'язкові налаштування перед запуском

| Змінна | Де взяти |
|---|---|
| `BOT_TOKEN` | [@BotFather](https://t.me/BotFather) → `/newbot` |
| `BOT_USERNAME` | юзернейм бота без `@` — потрібен для реферальних посилань |
| `ADMIN_CHAT_ID` | ID групи для замовлень; додайте [@getmyid_bot](https://t.me/getmyid_bot) у групу |
| `ADMIN_IDS` | ваш Telegram ID через кому — доступ до `/stats` і кнопок статусу |
| `JWT_SECRET` | `openssl rand -hex 32` |
| `DASHBOARD_PASSWORD` | змініть обов'язково — це єдиний захист панелі |
| `CARD_NUMBER`, `CARD_HOLDER` | реквізити для оплати переказом |
| `PUBLIC_URL` | адреса сайту — без неї кнопка Mini App не з'явиться |

`BOT_USERNAME` і `PUBLIC_URL` тепер обов'язкові: перший потрібен для кнопки
переходу з групи в особистий чат, другий — для адреси вітрини `/app`.

### Нова пошта

Ключ API з кабінету перевізника (Налаштування → Безпека → Ключі API) дає
вітрині показувати покупцеві список населених пунктів і відділень замість
двох вільних рядків. Задається в панелі: **Налаштування → Доставка**.

Ключ приймається, але назад не читається — панель показує лише стан
«підключено». Це навмисно: ним створюють накладні від імені магазину, тож
у відповіді API йому не місце. Щоб замінити — впишіть новий, щоб
відключити — очистіть поле й збережіть.

Без ключа форма замовлення працює як раніше: місто й відділення
вписуються руками, і такі замовлення приймаються далі. Перше, що варто
зробити після налаштування, — відкрити вітрину й спробувати знайти своє
місто: якщо перелік порожній, шукайте в журналі `novaposhta.rejected` —
там буде причина відмови словами перевізника.

Для попереднього розрахунку доставки потрібні ще два поля в тому ж
розділі: **місто відправлення** (назвою, як у довіднику) і **припущена
вага позиції**. Точної ваги товарів у каталозі немає, тому число, яке
бачить покупець, подається як приблизне й супроводжується проханням
уточнити суму в менеджера. Без міста відправлення показується «від N
грн» із поля «Доставка від».

### Відповіді бота в групах

Бот сам відповідає в групових чатах, коли впізнає питання про доставку,
оплату чи повернення. Це корисно в клієнтському чаті й заважає в
робочому: розмова команди про доставку щоразу викликала довідку про
доставку.

Перемикач — **Налаштування → Telegram-група → Відповіді на ключові слова
в групах**. Вимкнений, бот мовчить, поки до нього не звернуться прямо
через `@`: пряме звернення лишається робочим завжди, бо мовчання у
відповідь на особистий заклик виглядає як поломка, а не як тиша за
налаштуванням.

### Скасування замовлення

Покупець скасовує сам, поки замовлення нове або прийняте. Далі — ні:
оплачене означає, що гроші вже в нас, відправлене — що посилка їде.
Обидва випадки вимагають людини, тож із них вітрина веде в чат
замовлення. Менеджер скасовує з будь-якого робочого статусу — кнопкою в
рядку списку або на сторінці замовлення.

Скасування повертає товар у наявність і списані бонуси на рахунок, а в
чат команди надсилає окреме повідомлення: менеджер, який саме пакує
посилку, у список замовлень не дивиться.

Параметри магазину (`REFERRAL_PERCENT`, `BONUS_MAX_PERCENT`, `MIN_AGE`,
`SHOP_NAME`, `CURRENCY`, `CARD_*`) лишаються в `.env` як **значення за
замовчуванням**. Щойно їх змінюють у панелі («Налаштування»), значення з бази
перекриває змінну оточення. Порожня змінна = не задана, дефолт застосується.

## Тести

```bash
cd backend
python tests_repo.py     # перевірки логіки репозиторію
python tests_api.py      # перевірки HTTP
python tests_bot.py      # 61 перевірка діалогу бота
```

`tests_bot.py` працює зі справжнім диспетчером aiogram — транспорт Telegram
підмінено перехоплювачем, який записує виклики Bot API. Тому перевіряється не
«чи не впало», а що саме бот відповів: текст повідомлення, вміст кнопок,
сповіщення адміну, стан бази після кроку.

Окремий набір `qa/qa_scheduler.py` перевіряє відкладені розсилки: відбір
дозрілих, тихі години по обидва боки переходу на літній час, ретенцію
бекапів і те, що повторний тік не перезапускає вже надіслане.

### Рішення, які варто знати

**База за інтерфейсом.** Хендлери й роутери працюють з `Repository` і не
знають, як влаштоване сховище. Правило межі: в інтерфейс потрапляють операції
предметної області (`count_segment`, `adjust_stock`), а не запити — інакше SQL
протікає в контракт і межа перестає бути межею.

Колись за цим інтерфейсом стояли дві реалізації, Postgres і Firestore.
Firestore прибрано разом із serverless-розгортанням: на власному сервері
зовнішня база — це ще один сервіс, який відмовляє незалежно від магазину.
Абстракцію лишено — вона окупилась не переносимістю, а тим, що бізнес-логіку
можна тестувати без бази взагалі.

**Денормалізовані лічильники.** `orders_count`, `total_spent`, `referrals_count`
у клієнта, `products_count` у категорії. Оновлюються при записі, атомарними
інкрементами: список клієнтів більше не робить JOIN на кожен показ.

**Age gate — це middleware, не хендлер.** Поки `age_confirmed = false`, крізь
проходить лише `/start` і колбек підтвердження. Не обійти ні через deep link,
ні через inline-кнопку зі старого повідомлення.

**Бонуси — журнал, не лічильник.** Кожен рух пишеться окремим записом
(нарахування, списання, повернення), тому баланс завжди можна перерахувати.
Прапорець `referral_paid` гарантує, що винагорода нарахується один раз, навіть
якщо статус перемикати туди-сюди.

**Скасування відкочує все:** залишки на склад, бонуси клієнту, лічильники покупок.

**Статус як доріжка етапів.** У таблиці замовлень статус — не випадний список,
а рейка: видно поточний етап і пройдений шлях. Клік переводить далі й одразу
сповіщає клієнта.

**Розсилка порціями з курсором.** Курсор живе в самій розсилці, тому процес
можна обірвати будь-коли. На сервері порції крутить фонове завдання, у
serverless — планувальник. Усередині порції відправка паралельна (8 потоків)
з дотриманням ліміту 25 повідомлень/с.

Лишається доробити:

  прикрутити API для пошуку відділень і створення ТТН

- **Логування дій адміністраторів** — хто і коли змінив статус чи ціну
- **Моніторинг** — Uptime Kuma на `/api/health`

## Про оплату

Вбудовані Telegram Payments для цієї категорії товарів недоступні: LiqPay,
WayForPay, Stripe та інші еквайри забороняють нікотинову продукцію у правилах
для мерчантів. Тому в боті реалізовано ручні способи — переказ на картку з
надсиланням квитанції та накладений платіж. Якщо в майбутньому знайдеться
провайдер, який працює з цією категорією, точка інтеграції — крок
`Checkout.payment` у `bot/handlers/checkout.py`.

## Про вік і законодавство

Підтвердження 18+ вбудоване як обов'язковий крок і не обходиться. Врахуйте
також, що з 11.07.2023 в Україні (Закон № 1978-IX) діють обмеження на обіг
ароматизованих рідин та заборона реклами й стимулювання продажу електронних
сигарет — це стосується того, як оформлені картки товарів і тексти розсилок.
Питання відповідності конкретного асортименту й формулювань варто узгодити з
юристом; технічна частина панелі дозволяє редагувати всі тексти без правок коду.
