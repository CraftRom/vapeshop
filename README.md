# Телеграм-магазин: бот + дашборд

Магазин у Telegram із веб-панеллю керування. Бот на aiogram 3, API на FastAPI,
панель на React. Спільне ядро (`backend/shop/`) — щоб бот і дашборд працювали
з однією логікою і не розходились у поведінці.

---

## Що вміє

**Бот**
- Підтвердження віку 18+ на першому кроці — без нього каталог недоступний
- Каталог: категорії → товари з пагінацією, фото, залишками
- Кошик із зміною кількості прямо в картці товару
- Оформлення: ім'я → телефон → місто → адреса → промокод → бонуси → оплата → підтвердження
- Оплата переказом на картку з надсиланням квитанції, або накладений платіж
- Профіль: історія замовлень, бонусний баланс, реферальне посилання
- Реферальна програма: % бонусами від кожного виконаного замовлення запрошеного
- Кнопки зміни статусу просто в адмін-чаті, куди падають нові замовлення

**Дашборд**
- Огляд: виручка, середній чек, нові замовлення, графік по днях, топ товарів
- Замовлення: фільтри, пошук, зміна статусу, нотатки менеджера
- Каталог: CRUD товарів і категорій, швидка зміна залишків, індикатор «закінчується»
- Клієнти: історія покупок, ручне нарахування бонусів, блокування
- Промокоди: відсоткові та фіксовані, ліміти загальні й на клієнта, термін дії
- Розсилки: 6 сегментів, попередній підрахунок охоплення, прогрес наживо

## Розгортання

**Покроковий посібник для обох сценаріїв — [docs/DEPLOY.md](docs/DEPLOY.md).**
Там усе від створення бота до перевірки, що замовлення доходить у групу.

| | Vercel | Власний сервер |
|---|---|---|
| База | Firestore ([docs/FIREBASE.md](docs/FIREBASE.md)) | Postgres |
| Бот | вебхук | polling |
| Розсилки | порціями, планувальник | фоном, без пауз |
| Кому підходить | перевірити ідею | бойовий магазин |

Обирається однією змінною `DB_BACKEND`. Панель і API завжди на одному домені —
інакше панель не знайде бекенд.

Бізнес-логіка від бази не залежить: бот і API працюють через інтерфейс
`Repository` з двома реалізаціями, а тести перевіряють, що вони поводяться
однаково.

### Локальний запуск (розробка)

```bash
cp .env.example .env
nano .env                    # заповніть BOT_TOKEN, ADMIN_IDS, паролі

docker compose up -d --build
docker compose exec bot python seed.py     # демо-каталог (за бажанням)
```

Дашборд: `http://localhost` — логін і пароль з `.env`.
API-документація: `http://localhost:8000/docs`.

### Без Docker

```bash
cd backend
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
export PYTHONPATH=$PWD

alembic upgrade head                             # схема бази (для DB_BACKEND=sql)
python -m bot                                    # термінал 1
uvicorn api.main:app --reload --port 8000        # термінал 2

cd ../dashboard && npm install && npm run dev    # термінал 3
```

## Обов'язкові налаштування перед запуском

| Змінна | Де взяти |
|---|---|
| `BOT_TOKEN` | [@BotFather](https://t.me/BotFather) → `/newbot` |
| `BOT_USERNAME` | юзернейм бота без `@` — потрібен для реферальних посилань |
| `ADMIN_CHAT_ID` | ID групи для замовлень; додайте [@getmyid_bot](https://t.me/getmyid_bot) у групу |
| `ADMIN_IDS` | ваш Telegram ID через кому — доступ до `/stats` і кнопок статусу |
| `JWT_SECRET` | `openssl rand -hex 32` |
| `DASHBOARD_PASSWORD` | змініть обов'язково — це єдиний захист панелі |
| `CARD_NUMBER`, `CARD_HOLDER` | реквізити для оплати переказом |

Параметри магазину: `REFERRAL_PERCENT` (скільки % отримує реферер),
`BONUS_MAX_PERCENT` (яку частку замовлення можна закрити бонусами).

## Тести

```bash
cd backend
python tests_repo.py     # 62 перевірки логіки × 2 бази
python tests_api.py      # 60 перевірок HTTP × 2 бази
python tests_bot.py      # 61 перевірка діалогу × 2 бази
```

Разом 366 перевірок. Кожен набір ганяє один сценарій через Postgres і через
Firestore, а потім окремо звіряє результати: якщо реалізації почнуть
розходитись, тест назве конкретну перевірку.

`tests_bot.py` працює зі справжнім диспетчером aiogram — транспорт Telegram
підмінено перехоплювачем, який записує виклики Bot API. Тому перевіряється не
«чи не впало», а що саме бот відповів: текст повідомлення, вміст кнопок,
сповіщення адміну, стан бази після кроку.

Проти справжнього Firestore (потрібен емулятор):

```bash
firebase emulators:start --only firestore
FIRESTORE_EMULATOR_HOST=localhost:8080 python tests_repo.py --real
```

### Рішення, які варто знати

**Дві бази за одним інтерфейсом.** Хендлери й роутери працюють з `Repository`
і не знають, Postgres це чи Firestore. Правило межі: в інтерфейс потрапляють
операції предметної області (`count_segment`, `adjust_stock`), а не запити.
Інакше SQL протік би в контракт і Firestore його не реалізував.

**Денормалізовані лічильники.** `orders_count`, `total_spent`, `referrals_count`
у клієнта, `products_count` у категорії. Firestore не має JOIN і GROUP BY, тому
рахувати їх при читанні неможливо — оновлюємо при записі, атомарними
інкрементами. SQL від цього теж виграв: список клієнтів більше не робить JOIN.

**Гроші в копійках у Firestore.** Немає типу Decimal, а float для грошей —
джерело помилок округлення. Конвертація на межі репозиторію; бізнес-логіка
як і раніше бачить `Decimal`.

**Age gate — це middleware, не хендлер.** Поки `age_confirmed = false`, крізь
проходить лише `/start` і колбек підтвердження. Не обійти ні через deep link,
ні через inline-кнопку зі старого повідомлення.

**Бонуси — журнал, не лічильник.** Кожен рух пишеться окремим записом
(нарахування, списання, повернення), тому баланс завжди можна перерахувати.
Прапорець `referral_paid` гарантує, що винагорода нарахується один раз, навіть
якщо статус перемикати туди-сюди.

**Скасування відкочує все:** залишки на склад, бонуси клієнту, лічильники покупок.

**Статус як доріжка етапів.** У таблиці замовлень статус — не випадний список,
а рейка: видно поточний етап і пройдений шлях. Клік переводить далі й одразу
сповіщає клієнта.

**Розсилка порціями з курсором.** Курсор живе в самій розсилці, тому процес
можна обірвати будь-коли. На сервері порції крутить фонове завдання, у
serverless — планувальник. Усередині порції відправка паралельна (8 потоків)
з дотриманням ліміту 25 повідомлень/с.

## Перед виходом у продакшн

Три пункти з попередньої версії README вже закриті:

- ✅ **Alembic** — міграції налаштовані, `create_all` у продакшні не працює
- ✅ **Redis для FSM** — вмикається через `REDIS_URL`
- ✅ **Закритий API, HTTPS, бекапи** — у `deploy/` (див. docs/SERVER.md)

Лишається доробити:

- **Нова Пошта** — поля `delivery_city` / `delivery_address` уже є, лишається
  прикрутити API для пошуку відділень і створення ТТН
- **Кілька адмінів** з ролями замість одного логіна в `.env`
- **Логування дій адміністраторів** — хто і коли змінив статус чи ціну
- **Моніторинг** — Uptime Kuma на `/api/health`

## Про оплату

Вбудовані Telegram Payments для цієї категорії товарів недоступні: LiqPay,
WayForPay, Stripe та інші еквайри забороняють нікотинову продукцію у правилах
для мерчантів. Тому в боті реалізовано ручні способи — переказ на картку з
надсиланням квитанції та накладений платіж. Якщо в майбутньому знайдеться
провайдер, який працює з цією категорією, точка інтеграції — крок
`Checkout.payment` у `bot/handlers/checkout.py`.

## Про вік і законодавство

Підтвердження 18+ вбудоване як обов'язковий крок і не обходиться. Врахуйте
також, що з 11.07.2023 в Україні (Закон № 1978-IX) діють обмеження на обіг
ароматизованих рідин та заборона реклами й стимулювання продажу електронних
сигарет — це стосується того, як оформлені картки товарів і тексти розсилок.
Питання відповідності конкретного асортименту й формулювань варто узгодити з
юристом; технічна частина панелі дозволяє редагувати всі тексти без правок коду.
