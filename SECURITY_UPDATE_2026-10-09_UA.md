# Звіт про перевірку та посилення безпеки — 09.10.2026

Оновлено вихідний код, міграції, конфігурацію розгортання та перевірки для дашборду, вітрини, API і Telegram-бота. Роботу виконано на повному проєкті попередньої версії. На робочий VPS ці зміни ще не встановлено.

Версії: дашборд **1.65.0**, вітрина **2.18.1**, API **1.18.0**, бот **1.15.1**. Нова міграція: `e8b30a2d9071_security_sessions`, після `d7a24c10b853_catalog_taxonomy`.

## Виявлено та виправлено

| Ділянка | Проблема | Реалізована зміна |
| --- | --- | --- |
| Вхід у дашборд | Bearer-токен зберігався в доступному JavaScript сховищі | Браузер використовує випадкову HttpOnly-сесію. У HTTPS: `__Host-` cookie, `Secure`, `SameSite=Strict`, `Path=/`, без Domain. У БД зберігається SHA256-відбиток ідентифікатора, а не cookie |
| Запити дашборду | Для cookie потрібен захист від запитів сторонніх сайтів | Випадковий CSRF-токен на сесію, перевірка заголовка, Origin і Fetch Metadata для запису; окремий захист входу від login CSRF. CSRF живе у памʼяті вкладки |
| Вихід і зміна пароля | Вихід лише очищав браузер; зміна пароля менеджера не відкликала старий JWT | Сервер видаляє сесію при виході; версія облікових даних відкликає cookie/JWT після зміни пароля та вимкнення менеджера. Повторне ввімкнення потребує нового входу |
| Строк сесії | Розрахунок лише на строк токена | Серверна абсолютна межа за `JWT_TTL_HOURS` (1–72 год), неактивність авторизованих API-запитів — `DASHBOARD_IDLE_MINUTES` (за замовчуванням 60 хв). Сесія обертається при повторному вході |
| Права та realtime | Довгий потік міг залишатися відкритим після відкликання доступу | Права звіряються з БД; SSE повторно перевіряє сесію на подіях і heartbeat. Зміна ролі діє на сервері |
| JWT для API-клієнтів | Неповні або некоректні claims могли розбиратися ненадійно | Обовʼязкові issuer, audience, строки, subject, роль, ідентифікатор і версія облікових даних. Хибний Bearer не переходить на cookie. Bearer-вхід збережено для API-клієнтів, браузер ним не користується |
| Telegram Mini App | Без `auth_date` перевірка строку не виконувалася; нетипові user/hash могли спричинити помилку | Обовʼязковий час, HMAC і формат підпису; відхилення дублікатів усіх полів; перевірка структури користувача та додатного числового ID. Чинний строк Telegram-сесії 24 год збережено |
| Telegram webhook | Захисний заголовок був необовʼязковим; його можна було обчислити зі шляху | Заголовок обовʼязковий. Секрет заголовка отримується HMAC із незалежним серверним ключем. Некоректний JSON/update відхиляється як 400 |
| Зображення | Перевірка кількох початкових байтів пропускала підробки | Повне декодування JPEG/PNG/GIF/WebP, повторне кодування без EXIF та прихованих дописок; межі 8 МБ, 20 Мп, 8192 px, 100 кадрів / 32 Мп сумарно. Безпечні анімації збережено. Квитанції у вітрині також проходять цю перевірку |
| Зберігання медіа | Пряма файловa операція та неповний контроль роздачі | Атомарне збереження, відхилення symlink, правильне повторне використання файлу. Nginx дозволяє лише растрові розширення, блокує symlink, віддає nosniff та sandbox-політику |
| Запити й імпорт | Стиснений XLSX або великий/chunked запит міг споживати зайві ресурси | Ліміти фактичного тіла запиту; авторизація multipart до читання тіла; не більше 4 одночасних multipart. XLSX: 10 МБ, до 1000 ZIP-записів, 64 МБ розпакування, до 50 000 рядків, захищений XML-парсер |
| Бекапи | Велике завантаження потребує окремого бюджету й прав | До 200 МБ файлу / 201 МБ multipart; перевірка системного адміністратора до читання; проміжне велике тіло розміщується на томі бекапів |
| Хости, проксі та CORS | Заголовок IP приймався без перевірки джерела; занадто широкі політики | Перевірка Host; невідомі домени Nginx закриває. Динамічні промо обслуговуються двома публічними маршрутами та звіряються з опублікованими сторінками. IP-заголовки приймаються лише від довірених проксі. CORS — точні origin, методи та заголовки |
| Журнали і відповіді | Секрети могли потрапляти у шлях, query, Referer чи помилки валідації | Маскування webhook-шляхів і секретних параметрів; Referer без query/fragment. Access log Nginx без сирих query і секретів вебхуків. Вимкнено сирий access log Uvicorn. 422 не повертає введені паролі; приватні API-відповіді мають no-store |
| Політики сторінок | Частина заголовків губилася при успадкуванні; промо дозволяло будь-який inline JS | Відновлено Permissions-Policy та заборону cross-domain policy на дашборді й вітрині. Промо HTML має SHA256-allowlist серверних inline-скриптів; збережено інтеграції Google. CSP вітрини дозволяє SDK та iframe Telegram |
| Конфігурація запуску | Запуск поза deploy-скриптом міг залишити слабкі production-секрети | Для налаштованого HTTPS-сайту API відмовляється стартувати з коротким/шаблонним JWT-ключем чи паролем власника |
| Залежності | Аудити показали відомі вразливості | FastAPI 0.143.0, Starlette 1.7.0, PyJWT 2.15.0, Pillow 12.3.0, defusedxml 0.7.1; React Router 7.18.4 і виправлення source-map-js. Додано зафіксовані Python-залежності для production-образу. Nginx 1.30.5 Alpine зафіксовано версією та digest |

Колірна схема, юридична сторінка й віковий екран залишені без змін. Категорії, субкатегорії, SKU, новинки, акції та редагування товару з попереднього етапу збережені.

## Як встановити оновлення

1. Зробити резервну копію БД та `.env`, розпакувати повний архів проєкту.
2. Перевірити `.env`: `PUBLIC_URL=https://...`, випадковий `JWT_SECRET` не коротший за 32 символи, пароль власника не коротший за 12 символів, без `change...`/`your_...` заглушок. `CORS_ORIGINS` має містити точні потрібні origin. Перевірити мережі `TRUSTED_PROXY_NETWORKS` відповідно до Docker.
3. Запустити штатний `deploy/deploy.sh`. Він застосує міграцію перед API; нові backend і dashboard слід встановлювати разом. Старі сесії попередньої версії вимагатимуть нового входу.
4. Якщо Telegram працює через **webhook**, повторно виконати захищений `telegram-setup`, щоб Telegram отримав новий secret_token. У polling-режимі це не потрібно. Ротація JWT_SECRET також потребує повторного webhook setup. Після налаштування перевірити доставку реального апдейта.
5. На сервері перевірити `nginx -t`, здоровʼя сервісів, HTTPS, вхід/вихід і створення тестового товару. Перевірити відкриття Mini App у Telegram Web та на телефоні.

Для локальної HTTP-розробки використовується окрема HttpOnly-cookie без Secure. Production-cookie залежить від HTTPS `PUBLIC_URL`; це значення має бути правильно налаштоване у середовищі.

## Межі перевірки

Немає доступу до робочого VPS, його firewall/SSH, реальних секретів, журналів, Cloudflare, встановлених образів чи даних production PostgreSQL. Локальні тести не замінюють перевірку цих компонентів після деплою. Живі платежі й доставку через справжній Telegram/CRM не виконували.

Захист API й браузерних сесій реалізовано в коді. MFA/2FA та зовнішній WAF у цьому оновленні не впроваджувалися. Окремо можна налаштувати багатофакторний доступ для власника та панелі через провайдера доступу. Відомо оприлюднені ключі потрібно замінити у відповідного провайдера; це оновлення не обертає зовнішні ключі автоматично.
