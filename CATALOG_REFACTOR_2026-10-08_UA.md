# Оновлення каталогу — 08.10.2026

Версії: вітрина **2.18.0**, панель **1.64.0**, бот **1.15.0**.

## Зроблено для замовника

- Додано два рівні групування: категорії та субкатегорії. Старі категорії переносяться в субкатегорії зі збереженням їхніх ID, назв, описів, порядку та зв’язків із товарами.
- У панелі можна створювати та редагувати обидва рівні, призначати або прибирати батьківську категорію субкатегорії, приховувати групи. Категорія показує також товари її субкатегорій.
- Товар може бути без груп, лише з категорією, лише із субкатегорією або з обома. Товари без груп доступні у загальному каталозі та окремому фільтрі.
- Замість великого вікна редагування є окрема сторінка товару. Незалежні блоки: основне та відображення, категорія/субкатегорія, ціни/акція, зображення, опис. Кожен блок зберігає тільки свої поля; помилка залишає введені дані у формі.
- Оновлено вікно «Новий товар»: згруповані поля, необов’язкові категорії, налаштування видимості й новинки, ціна, акція, залишок, опис і зображення. Артикул створює система.
- Новинки керуються збереженим перемикачем `is_new`, а не датою створення чи порядком у списку. Вимкнення перемикача прибирає позначку та товар із відповідного відбору.
- Акція керується перемикачем `is_sale`. Для активної акції стара ціна має бути більшою за поточну; позначки й перекреслена ціна однакові у панелі, вітрині та боті.
- Додано пошук за артикулом, відбір за категорією/субкатегорією, новинками, акціями та відсутністю груп. Збережено швидке редагування залишків, масові дії та імпорт/експорт.
- Оновлено бот: навігація категоріями/субкатегоріями, усі товари, новинки й акції. Старі посилання на категорії ведуть до перенесених субкатегорій.
- Зображення, збережені як Telegram-фото, доступні також у панелі через авторизований API. При заміні зображення старе Telegram-фото не підміняє нове.
- Ціни з копійками збережені у вітрині, панелі та повідомленнях бота.
- Кольори та погоджені раніше тексти підтвердження віку й юридичних сторінок збережено.

## Правила SKU

Новий товар завжди отримує унікальний системний SKU формату `ELF-<код групи>-<8 символів>`. Для коду беруться латинські літери та цифри назви субкатегорії або категорії; якщо їх немає, використовується `GEN`. При випадковій колізії вставка повторює генерацію. Ручний SKU при створенні не стає системним артикулом; редагування товару його не змінює.

Чинне правило для вже наявних артикулів: **3–32 символи**, перший — велика латинська літера або цифра, решта — великі латинські літери, цифри, `.`, `_`, `-`. Коректні артикули зберігаються.

Одноразова міграція прибирає крайні пробіли та переводить некоректний регістр у верхній, якщо результат відповідає правилу й вільний. Для решти генерується `ELF-LEG-<ID товару>` з унікальним суфіксом за потреби. Початкове значення зберігається у `external_sku`.

Імпорт також генерує системний артикул для нових товарів. Зовнішні артикули зберігаються окремо; повторний імпорт оновлює знайдений товар без зміни його системного SKU. Неоднозначний зовнішній артикул або назва повертають помилку рядка. Власний XLSX зберігає категорію, субкатегорію, її батьківську категорію, зовнішній артикул і позначки. Колишня єдина «Категорія» у SalesDrive імпортується як субкатегорія.

## Оновлення бази

Міграція: `backend/alembic/versions/d7a24c10b853_catalog_taxonomy.py`, після `c6a72f19e301`.

1. Зробити резервну копію поточної бази штатним механізмом розгортання.
2. Розгорнути всі компоненти з цього архіву разом. `deploy/deploy.sh` визначає необхідність зміни структури каталогу, перевіряє успішність бекапу й перед міграцією зупиняє старі API, бот і scheduler. Якщо бекап не створено, перехід зупиняється до вимкнення старих застосунків.
3. Штатний сервіс міграцій виконує `alembic upgrade head`: переносить групи, виправляє SKU, переносить наявні знижки в `is_sale`. Наявні товари не позначаються новинками автоматично.
4. Запустити нові компоненти та перевірити каталог у панелі й вітрині.

Для заповненого каталогу повернення до старої схеми потребує відновлення резервної копії. Скрипт розгортання не повертає старі образи поверх нової несумісної схеми; порожня база підтримує звичайний downgrade.

Робоча база у цій сесії не підключалася. Перенесення її категорій та виправлення її SKU відбудеться **під час застосування міграції**.

## Перевірка

Підсумкові результати: `qa/output/verification.json`; журнали повного прогону: `qa/output/catalog-regression-final.log`, `qa/output/catalog-browser-final.log`, `qa/output/backend-catalog-final/`.

Пройдено **74 набори backend**, **38 наборів Node**, **371 перевірку зв’язків** та **281 браузерну перевірку**. Обидва застосунки зібрані для production. Після останніх уточнень імпорту та розгортання їхні цільові набори повторно пройшли **12/12** і **6/6** відповідно.

Окремі сценарії перевіряють усі чотири варіанти групування товару, спільні новинки/акції, незалежне редагування блоків, захист SKU, колізію при створенні, імпорт/експорт, фото, переміщення субкатегорії та міграцію на заповненій SQLite-базі. Браузерні сценарії перевіряють панель і вітрину на мобільних та широких екранах, включно зі збереженням двох блоків із відповідями у зворотному порядку.

Міграцію перевірено на SQLite, включно з усім ланцюжком Alembic. Гілка PostgreSQL містить відновлення послідовності ID, але на живому PostgreSQL у цій сесії не виконувалася.

Повторення функціональних перевірок:

```bash
cd backend
pip install -r requirements-qa.txt
bash qa/run_all.sh
```

Повторення браузерних перевірок:

```bash
npm --prefix dashboard ci
npm --prefix miniapp ci
cd qa
npm install
npx playwright install chromium
npm test
```

Production-збірки: `npm --prefix dashboard run build` та `npm --prefix miniapp run build`.
