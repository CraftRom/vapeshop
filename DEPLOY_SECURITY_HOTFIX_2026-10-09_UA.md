# Виправлення зупинки деплою через DASHBOARD_PASSWORD

API 1.18.1, вітрина 2.18.2. Дата: 09.10.2026.

## Що показав наданий лог

Образи зібралися, перевірка імпорту backend пройшла, міграція `d7a24c10b853 → e8b30a2d9071` застосувалася. Новий API відмовився запускатися: `Небезпечна production-конфігурація: DASHBOARD_PASSWORD`. Скрипт запустив відкат основних контейнерів. У фрагменті немає успішної перевірки API після відкату, тому працездатність сервера після нього не підтверджена.

Причина в попередньому оновленні: перевірка перед деплоєм відхиляла лише кілька конкретних заглушок, а startup API вимагав пароль від 12 символів і відхиляв шаблонні префікси. Перевірка імпорту не запускала lifespan і не виявила розбіжність до міграцій. Значення пароля в логу відсутнє; точно встановити, чи він короткий, чи шаблонний, із цього фрагмента неможливо.

## Що виправлено

- Один модуль правил для перевірки на хості, фактичного середовища нового образу, startup API та відображення стану секретів у дашборді.
- Для HTTPS: `JWT_SECRET` від 32 символів, `DASHBOARD_PASSWORD` від 12; шаблонні `change*`/`your_*` відхиляються без урахування регістру. Помилки показують вимогу та назву змінної, без її значення.
- Невалідний пароль із кореневого `.env` зупиняє повний деплой ще до звернень до Docker, збірки й міграцій.
- Після збірки `python -m shop.preflight` перевіряє фактичні Settings образу, ключ Fernet та імпорт API. Повний деплой виконує це до міграцій; promo-only — до заміни контейнерів.
- Захист запуску API збережено. Поріг пароля не послаблювався. Локальна HTTP-розробка працює за попередніми правилами.

## Що зробити на сервері

1. Розпакувати повний оновлений проєкт, зберігши поточні `.env` та дані.
2. У **кореневому `.env`** замінити `DASHBOARD_PASSWORD` на новий випадковий пароль від 12 символів. Наприклад, `openssl rand -hex 16` генерує 32 символи: збережіть результат у менеджері паролів і впишіть у `.env`. Це змінить пароль входу власника; його старі сесії втратять чинність.
3. Не змінювати `JWT_SECRET`, пароль PostgreSQL чи Redis для усунення саме цього збою: лог указує на `DASHBOARD_PASSWORD`.
4. Із кореня проєкту виконати `bash deploy/deploy.sh`. Пароль більше не потрібно передавати в чат чи виводити через `docker compose config` без `--quiet`.
5. Після успішного деплою перевірити вхід у дашборд і API. Якщо API не запустився, із `deploy/` отримати `docker compose --env-file ../.env -f docker-compose.prod.yml logs --tail=80 api`.

Відкат контейнерів не повертає міграції БД. Для цієї помилки не потрібно видаляти томи, скидати БД або виконувати downgrade.

## Перевірки

- 9 тестів деплою й startup: короткі/шаблонні паролі, короткий JWT, лапки, мінімальна допустима довжина, блокування до Docker і до БД, перевірка фактичного середовища та коректний preflight без працюючої БД.
- Регресія безпеки: **61/61**; налаштування: **20/20**.
- Перевірка фаз деплою, звʼязності компонентів, синтаксису Bash/Python та залежностей.
- Логи: `qa/output/deploy-security-hotfix.log`, `deploy-hotfix-modern-security.log`, `deploy-hotfix-env.log`, `deploy-hotfix-phases.log`, `deploy-hotfix-wiring.log`.

Виправлення перевірене локально. Доступу до VPS і його `.env` немає; пароль на сервері не змінювався, повторний production-деплой не виконувався. Вітрина, включно з початковим вибором «Новинки», залишена у версії 2.18.2.
